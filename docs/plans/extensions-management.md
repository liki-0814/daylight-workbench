# Daylight 本地扩展管理技术方案

- 状态：已按用户实施指令落地；验收结果见[扩展管理验收报告](../verification/extensions.md)。
- 日期：2026-10-09。
- 实施基线：8275db8，先提交原暂存代码，再创建 codex/extensions-management 分支。设计最初基于 156250b 及当时工作区，以下代码位置是设计阶段定位。
- 范围：管理 ~/.agents 下的 Skill、MCP 主配置及其客户端接入关系；增加前端入口、管理 API、Daylight AI 管理工具、测试和原生打包支持。
- 交付边界：前端、API、AI 管理联动、恢复、仓库 Skill 与原生打包一并交付；测试使用隔离来源，不修改真实扩展或客户端配置，不替换已安装 App。

**1. 问题、目标和已确定边界**

目标是让用户在 Daylight 中维护一份本地扩展来源，并了解它们如何接入本机 AI 软件。Daylight AI 对话承担查询、解释、诊断和提出管理变更的职责。

已经明确的产品边界：

1. Skill 的唯一管理来源为 ~/.agents/skills。其他客户端中的独立副本、内置 Skill、插件包不纳入内容管理。
2. MCP 同样只管理 ~/.agents 下的主配置。其他客户端中的现有 MCP 配置不自动导入、迁移或覆盖。
3. 客户端原生读取主目录时不建立新链接；需要链接时只建立必要的接入关系。
4. 接入操作可以创建用户选定客户端的链接，但不把客户端目录作为第二个配置来源。
5. Daylight AI 可以管理这些扩展；本需求不要求新增会话能力选择器、自动装载全部扩展或更换现有 AI 运行目录。
6. 首版适配本机已核实的 Codex、Qoder、Pi。Cursor 不在支持范围内，不为其增加检测、适配、链接操作或验收项。已安装、格式兼容、已接入、运行时已发现分别判断。

MCP 主文件采用 ~/.agents/mcp/servers.json。这是 Daylight 的管理格式，不是各 CLI 已经共同遵循的标准。浏览时不创建目录；已有主文件先解析，格式错误时保留并停止对应写入。

**2. 前端入口与用户任务**

推荐主导航名称为「扩展管理」，放在「CLI 配置」之后、「设置」之前。当前主导航是任务、专注统计、AI 对话、反向代理、CLI 配置、设置，新入口沿用现有导航的文字长度和操作语气。

| 候选名称 | 判断 |
| --- | --- |
| 扩展管理 | 推荐。能包含 Skills 和 MCP，体现跨客户端的管理行为 |
| Skills / MCP | 直白，但像技术分类，不能自然承载客户端接入和问题诊断 |
| AI 能力 | 容易被理解为当前 Daylight 对话的能力选择或执行配置 |

页面说明：「管理 ~/.agents 下的 Skills 与 MCP，并连接到本机 AI 软件。」

页面内设置三个分类：Skills、MCP 服务、接入软件。Skills 默认打开；搜索、软件筛选和问题筛选保留在页面状态与 Hash 中，不写入任务 state。

| 分类 | 首屏展示 | 常用动作 | 展开后展示 |
| --- | --- | --- | --- |
| Skills | 名称、用途摘要、主目录相对路径、相关软件、问题提示 | 查看、编辑、接入软件 | SKILL.md、文件列表、链接目标、变更影响、已声明的 MCP 依赖 |
| MCP 服务 | 名称、stdio/HTTP、接入软件、最近检测结果 | 查看、编辑、测试连接 | 参数、环境变量引用、工具目录、适配差异、生效方式 |
| 接入软件 | 检测到的软件及 CLI/桌面形态、Skill/MCP 接入方式 | 查看接入情况、预览接入变更 | 原生支持依据、链接与生成配置、冲突、刷新或重启说明 |

列表采用紧凑行和分区，详情在宽屏侧面展开、窄屏进入独立详情层。编辑用明确的保存/取消；删除首版采用归档，操作名称直接说明「归档主 Skill，影响使用它的软件」。解除客户端链接、归档主内容是两个不同动作。

不设置含义模糊的 Skill 全局「启用」开关。原生读取整个主目录的客户端可能不支持逐个排除，隐藏一条列表记录也不能阻止它加载文件。接入按钮只表示建立关系；无法在当前范围内实现的按软件禁用，显示限制，不用虚假的开关模拟。

新建 Skill 可输入名称、用途和初始内容；本地导入必须由用户明确选择，目标仍在主目录。查看文件不执行 scripts。第三方包更新、远程市场安装、自动 Git 提交不进入首版。

路由建议：

- #extensions&tab=skills
- #extensions&tab=skills&id=稳定对象ID
- #extensions&tab=mcp&id=稳定服务ID
- #extensions&tab=clients&client=qoder

浏览器返回、刷新和详情直达应保留分类、搜索及软件筛选。对象已归档或删除时显示原因和返回入口，不跳到一个同名对象。

**3. 已核实的基础与兼容性边界**

仓库已经具备以下基础：

| 位置 | 已有职责 | 本次使用方式 |
| --- | --- | --- |
| public/components/sidebar.js:3、public/routes.js:7、public/app.js:42 | 主导航、Hash 解析、页面生命周期 | 注册新页面，保留旧导航语义 |
| public/components/section.js:8、dialog-shell.js:2、segmented-control.js:2 | 标题、刷新、对话框、分类切换 | 复用布局与键盘行为 |
| core/contracts.js:18、core/web-assets.json | Node/Swift 共用路由、鉴权类别及静态资源允许列表 | 统一登记接口和资源 |
| ai/tools/dispatch.mjs:9、ai/drafts.mjs:6 | AI 查询及审阅应用 | 新增扩展查询和扩展变更草稿 |
| ai/run-manager.mjs:15、ai/store.mjs:13 | 待确认运行及重启处理 | 复用交互，另持久化已提交扩展请求 |
| native/Server.swift:245、native/Proxy.swift | 原生请求转发与 Node helper 生命周期 | 复用现有 helper 传输 |
| scripts/build-native.py:25、scripts/trim-runtime.mjs:12 | App 资源复制和依赖裁剪 | 纳入新增模块，验证实际安装包 |

当前 AI 发送会沿用 ai/store.mjs:33 的独立 workspace，现有 Skill 选择通过本机后端发现。管理目录不能直接替换这些运行语义。新模块的目录清单也不能替代原生后端的 Skill 清单，后者可能含内置或插件 Skill。

设计阶段只检查安装路径和目录元数据，没有启动客户端会话或 MCP 服务；以下为设计快照，实施验收证据另见报告：

- 首版范围内，PATH 中发现 Codex、Qoder、Pi；桌面目录发现 Qoder、Daylight 等应用。
- ~/.agents/skills 中有 20 个一级条目；Codex、Qoder、Pi 的专属 Skill 目录已有指向主目录的链接。
- Codex 官方文档支持 ~/.agents/skills；本机 Pi 1.1.0 随包文档也声明支持该目录。
- Qoder 官方 Skill 文档使用 ~/.qoder/skills；本机已有相关链接。实施时仍应依据安装版本进行接入验证。

这些结果是本机快照。适配器结构可扩展，但新增支持软件需要另外确定范围，不能因为扫描到应用就自动增加适配任务。目录条目数不等于有效 Skill 数，安装路径存在也不等于软件已发现扩展。

原生支持的软件保持零新增链接。已经存在的旧链接仅展示为「已有接入」，不因支持原生目录而自动清理。用户要求整理时再单独生成清理预览。

MCP 不能直接套用 Skill 的目录链接方式：Codex 将 MCP 表嵌入 config.toml，Qoder 的用户 MCP 配置位于 settings.json，各客户端还可能支持独立配置、启动参数或插件入口。软链接不会转换 JSON/TOML，也不能只链接一个混合配置文件的子字段。

因此，严格保持 ~/.agents 为管理范围时：

| 接入类型 | 处理方式 |
| --- | --- |
| 原生读取主配置 | 记录并验证，不写外部文件 |
| 支持专用 MCP 配置文件且允许链接 | 在 ~/.agents 生成对应格式，只链接该专用文件；已有文件冲突时不覆盖 |
| 支持独立配置或启动参数 | 生成配置与可复制的接入方式，标明只对该启动方式生效；不改 PATH、不替换原命令 |
| MCP 嵌在包含其他设置的全局文件中 | 显示「需客户端接入」。在本轮边界下不自动编辑该文件，由用户在客户端完成接入 |
| 未验证或当前版本不支持 | 显示原因，禁用无效操作；不把生成成功写成接入成功 |

对于必须改外部全局 MCP 配置才能默认生效的软件，「只写主目录」与「普通启动自动生效」不能同时承诺。首版选择遵守主目录边界；如果之后需要无感接入，再讨论仅修改指定 MCP 配置段的例外。整份全局配置文件软链接不作为默认方案。

**4. 主目录、数据权威与对象身份**

建议新增内容均位于 ~/.agents 内：

| 路径 | 职责 | 是否权威来源 |
| --- | --- | --- |
| skills/<skill目录>/ | SKILL.md、脚本、资源、引用文件 | 是 |
| mcp/servers.json | MCP 服务及公开配置、环境变量引用 | 是 |
| mcp/generated/<client>/ | 从主配置生成的客户端格式 | 否，可重建 |
| daylight/bindings.json | 用户选择的接入关系、操作归属和实际链接目标 | 接入意图的权威记录 |
| daylight/operations/<requestId>.json | 写入回执、恢复状态、文件前后摘要及完整快照 | 操作恢复依据和恢复材料；不再另存 backups 副本 |
| archive/skills/、archive/mcp/ | 已归档来源 | 不作为可发现来源 |

首次打开页面只读，目录不存在时展示空状态；直到用户执行保存或接入操作才建立本工具所需目录。用户已有非本工具文件保留，不能以一个初始化模板覆盖。

不把 Skill 正文或 MCP 主配置复制到 Daylight 的 state.json、focus.json、AI settings.json 中。缓存只保存派生清单，可删除重建。已有对话可以保存引用和操作摘要，但不成为扩展配置来源。

Skill 对象使用源目录关联的稳定 ID，展示名和 frontmatter.name 不是唯一主键。已有源目录重命名时需要显式操作维护身份；手动移动导致无法确认身份时提示重新关联，不通过同名猜测。客户端中指向同一个 realpath 的链接作为同一来源的接入关系，不重复计数。

MCP 服务 ID 与客户端展示名分开。生成名称碰撞、客户端字段不支持、stdio/HTTP 不兼容必须预检。全局禁用只表示主配置和新生成配置排除该服务，不意味着已经运行的外部客户端立刻断连。

Skill 与 MCP 的依赖只采用 Skill 已明确声明的元数据或用户确认的依赖关系；不从名称、用途文本推断。MCP 移除时展示依赖 Skill，不自动删除 Skill。未知依赖显示「未声明」，不称为「无依赖」。

首版凭据配置采用环境变量引用，不管理客户端 OAuth 登录，也不新增 Token 文件。主配置、生成文件、操作回执、AI 文本都不放凭据明文。若客户端无法按该方式提供凭据，标记接入限制；后续需要长期凭据管理时再复用现有 Keychain 基础，并隔离命名空间。

**5. 接入模型与状态表达**

首版只注册 Codex、Qoder、Pi 的适配器，按软件和安装版本描述能力；产品代码不散落软件名判断。

每个适配器最少提供 detect、describe、inspectBinding、planBinding、renderMcpConfig、verifyBinding。不存在的能力不伪装成空成功。Skill 和 MCP 分别声明：

- Skill：nativeRoot、symlink、unsupported/unknown；目标目录、是否识别链接、刷新方式。
- MCP：native、dedicatedFileLink、launchConfig、manual、unsupported/unknown；支持的传输、字段和凭据引用形式。

软件检测只读路径、应用元数据和受限的版本信息，不为了列出安装软件启动 AI、MCP 或登录流程。一个软件的桌面版和 CLI 可共享接入配置，先去重，再展示形态；VS Code 已安装不代表其中某个 AI 插件已安装。

状态分三层，而不是一个绿色「可用」：

| 层次 | 可报告的事实 |
| --- | --- |
| 主来源 | 有效、格式错误、归档、源文件变化 |
| 接入关系 | 原生支持、链接正确、同名冲突、链接失效、需启动参数、待客户端接入 |
| 运行验证 | 未检测、握手成功、目标客户端已发现、授权失败、启动失败；附时间和版本 |

MCP 握手成功只证明当前检测进程能连接并列出工具，不证明其他软件已加载，也不证明工具具有业务权限。文件生成成功和软链接正确都不能替代运行验证。

已有链接默认不算 Daylight 创建。用户可以在预览中明确接管匹配主来源的链接；之后才能由本工具自动解除。清理时核对记录和实际链接目标，链接被用户改写就停止，不删除实体目录或未知链接。

默认采用按 Skill 的链接，不替换整个客户端 skills 根目录。即使根目录已有用户内容，也能保留各自职责。同名实体目录、不同目标链接均显示冲突，不自动覆盖。

**6. 代码职责与依赖方向**

推荐沿用当前原生 WebView、原生 ES modules 和 Node helper。此功能没有引入 React、全局 Redux、插件框架或通用配置平台的必要。

新增模块以实际职责拆分：

| 建议文件 | 唯一主要职责 |
| --- | --- |
| core/extensions-contracts.js | 路由方法、公开 DTO、action 名称和无 IO 的校验约定 |
| extensions/service.mjs | 组装扩展管理服务，暴露 HTTP、prepare/apply/operations |
| extensions/catalog.mjs | 主来源索引、缓存失效、读取诊断 |
| extensions/skill-files.mjs | Skill 元数据与允许的文件读写计划 |
| extensions/mcp.mjs | 主配置规范化、客户端生成结果、受控握手检测 |
| extensions/bindings.mjs | 接入关系、冲突、链接归属和影响计算 |
| extensions/transactions.mjs | 写锁、文件摘要、暂存、回执和恢复 |
| extensions/clients/ | 小型适配器注册表与确有差异的客户端实现 |
| public/extensions/page.js | 页面组装、路由与可见性，不直接操作文件系统 |
| public/extensions/client.js | HTTP 客户端、统一错误和原请求重试 |
| public/extensions/controller.js | 页面状态、请求去重、变更通知与 dirty 表单保护 |
| public/extensions/skills.js、mcp.js、clients.js | 对应分类展示和交互；不重复保存规则 |
| public/extensions/review.js | 与 AI 对话共用的扩展变更审阅呈现 |
| public/extensions/extensions.css | 本页样式，复用 design-system token |
| ai/extensions-submissions.mjs | AI 草稿与持久提交恢复桥，不操作源文件 |

只有真正独立的职责才新增文件，短小实现可以先合并。所有目录不应为满足表格而预先填空壳。第三方 YAML 解析与 MCP 诊断 SDK 显式声明依赖并按现有打包策略处理；不依赖 Qoder 的传递依赖恰好存在，也不手写完整 MCP 协议。

依赖关系以文字约束：

1. 网页和 AI 工具调用同一个扩展服务。
2. 扩展服务组合来源索引、接入适配器和事务模块。
3. 适配器不了解任务 UI、AI 会话或代理来源；事务模块不了解软件名。
4. core 不导入 Node fs、SDK 或客户端私有实现，保证 JavaScriptCore 可加载。
5. proxy 和 cli/Pi 模型配置模块不承担扩展内容保存。AI adapter 不承担扩展文件管理。

Node 开发服务按需创建扩展服务。原生端复用已有 AI helper 的进程和转发能力，但把扩展服务与模型会话服务分开初始化：浏览扩展不应创建 AIStore、不应启动模型发现、不应受模型未登录或某个 SDK 初始化失败影响。

可在 ai/sidecar.mjs 内增加一个很小的服务分流，或提取同一分流函数供 Node 服务复用。原生共享契约把扩展请求路由到现有 helper，Swift 只做既有鉴权与 HTTP 转发，不再实现一套 Skill 文件规则。只有该分流确实不够清晰时再引入新的 helper 宿主，首版不增加常驻进程。

具体分流建议：扩展路由沿用 handler=ai 指向现有进程，额外声明 service=extensions，target 保留 /api/extensions 路径。Node 的装配层依据 service 调用 getExtensions 而非 getAI；Swift 沿用 handler 做传输，侧车依据 target 选择独立服务。这样不会为了查看扩展而经过 createAIService，也无需把文件业务复制到 Swift。额外路由字段必须进入两端合同测试。

打包时把 extensions 目录纳入 build-native.py 的资源复制和 trim-runtime.mjs 的裁剪目录；含 YAML/MCP npm 依赖的模块加入 build-runtime.mjs 的显式 bundle 入口，保留原模块路径和许可证记录。若诊断使用动态启动的 worker，必须像现有 ai/mcp-server.mjs 一样登记独立入口，不能仅以网页能导入作为入包证明。

扩展读取、检测和写入失败只降级这个模块。任务、日历、专注不能等待 Node helper，也不能在启动时依赖 ~/.agents 有效。

**7. API、写入和恢复**

网页入口为 /api/extensions，外部 Agent 入口为 /api/v1/extensions；两者由 core/contracts.js 描述方法与鉴权类别。网页写入验证 webToken 和 Origin，Agent 验证 Bearer；未知路径先鉴权再拒绝。

| 操作 | 接口建议 |
| --- | --- |
| 清单和软件接入状态 | GET /state |
| 读取受限的源文件或服务详情 | GET /objects/:id |
| 重新扫描主目录及接入元数据 | POST /refresh |
| 静态问题诊断 | GET /diagnostics |
| 准备变更 | POST /prepare |
| 应用已审阅变更 | POST /actions |
| 查询不确定结果 | GET /operations/:requestId |
| 取消或查询握手任务 | POST /probes、GET/DELETE /probes/:id |

prepare 返回 normalizedAction、expectedVersion、目标绑定的指纹、需要变更的文件、冲突、影响对象和生效方式。结果由服务端解析实际文件形成，不能只展示 AI 提供的说明。

actions 接收 requestId、expectedVersion 和明确 action；必要的审阅计划使用不可变 planId/摘要。重复请求必须绑定同一份规范化内容。版本同时覆盖主来源和本次涉及的接入文件状态，不能只看一个 Daylight 内存计数。

动作建议覆盖 skill.create/update/archive/restore，mcp.save/archive/restore，binding.connect/disconnect/adopt，operation.restore。暂不提供任意文件写入、任意命令、任意目标路径接口。对象 ID 与 clientId 由后端解析成已知路径。

写入顺序：

1. prepare 静态检查源文件、字段兼容性、链接归属和影响，不修改文件、不启动服务。
2. 用户审阅后提交；服务取得 ~/.agents/daylight 下跨进程排他锁，再读回相关指纹。
3. 先写暂存和恢复材料，记录 applying 回执，验证生成配置能被对应格式解析。
4. 分步原子替换单文件、创建或解除经过预检的链接；记录每步结果。
5. 读回文件和链接，完成 applied 回执，发布公开变更事件。
6. 崩溃恢复只恢复仍符合本次操作后置摘要的文件；外部已经改动时进入 recovery_required，展示具体步骤，不覆盖用户新内容。

单文件 rename 是原子的，多个目录、来源文件和客户端链接不是一个操作系统事务。方案使用暂存、日志和可恢复步骤，不能宣称任意故障下多文件同时原子提交。

同一 requestId 重试先查回执；响应丢失时界面展示「正在核对结果」，查询或重试原请求，不生成新 ID。409 保留用户输入并展示当前差异；拒绝盲目覆盖。

恢复是独立的扩展操作，带当前版本与前后内容检查，不复用任务 undo。归档不是永久删除，备份、生成目录、归档目录不能被当作新的可用 Skill 扫描。

文件范围按真实路径校验：源文件编辑不得越出 ~/.agents；源目录内指向范围外的链接不能被跟随写入。客户端侧只允许适配器计算出的必要链接位置，拒绝来自网页或 AI 的任意外部路径。检查目标与父路径的链接变化，不能用字符串 startsWith 作为目录边界判断。

**8. Daylight AI 管理联动**

用户可以直接在已有 AI 对话中表达管理请求：

- 「我有哪些本地 Skill？Qoder 能看到哪些？」
- 「检查 ~/.agents 里 MCP 的配置问题。」
- 「把这个 Skill 接入 Qoder，Codex 如果原生读取就不要操作。」
- 「解释这个 Skill 的用途，帮我修改描述，先让我看差异。」
- 「整理失效的接入链接，列出会影响哪些软件。」

工具保持少量、明确：

| 工具 | 行为 |
| --- | --- |
| daylight_get_extensions | 读取主来源清单、接入状态和公开版本 |
| daylight_get_extension | 按真实 ID 读取指定详情和允许的内容 |
| daylight_diagnose_extensions | 静态诊断；不启动 MCP、不修改配置 |
| daylight_propose_extension_changes | prepare 后生成待审阅卡，不能自行应用 |

实际 MCP 握手作为独立检测卡或上述 propose 工具的一种受控诊断动作。用户在页面点击「测试连接」表示发起一次检测；AI 发起时先展示服务、命令或端点并走相同确认行为。允许 initialize、能力协商、tools/list；不试调业务工具，不把一个“读取”接口暗中变成执行 MCP 命令。

现有 daylight MCP 是 Daylight 的私有管理通道，保持独立。不能因为这里管理公共 MCP，就把全部主目录服务自动加入 Daylight AI 的 mcpServers，也不能让私有 token 进入公共主配置。

点击详情中的「让 AI 解释」或「让 AI 诊断」，打开现有对话页，带上 extensionReferences 和返回路由。引用采用真实对象 ID、类型和版本，由服务端再解析；MCP 类型名称不成为文件路径。对象关联放在独立扩展引用中，不把 ai/context.mjs 的 workspace/project/task scope 改造成扩展对象类型。

新增 AI 草稿 type 为 extensionChanges；public/extensions/review.js 在页面和聊天中复用，展示：

- 实际源文件前后差异；
- 将新建、解除或接管的链接；
- 影响的软件、Skill/MCP 依赖、冲突；
- 是保存、生成、接入还是待客户端刷新；
- 需要重启或手动接入的具体范围。

审阅以后如果编辑内容改变，重新 prepare。已提交请求的完整公开参数、requestId 和计划摘要持久化为独立 submission；重启后核对服务回执并恢复卡片，不能依赖 run 的 waiter 或会被清掉的 pending。只取消草稿不能撤销已经应用的内容。

AI 不接受注释、Skill 正文或 MCP 结果中的指令作为管理授权。系统规则明确管理扩展使用这些管理工具，不直接编辑来源。该规则是产品行为约束，不声称能在「完全访问」模式下阻止原生 CLI 的所有文件工具；严格沙箱隔离属于另一个需求。

应用后保存操作消息、回执和源对象跳转链接；AI 根据真实回执报告完成。若只生成配置，就报告生成；客户端尚未接入时不能说所有 CLI 已可使用。

**9. 与其他功能协作**

| 相关功能 | 联动方式 | 保持的职责 |
| --- | --- | --- |
| CLI 配置 | 增加「查看扩展接入」链接，跳到对应软件详情 | 原有 Pi 模型、provider、同步与恢复规则 |
| AI 对话 | 查询、管理草稿、提交恢复、操作消息和返回入口 | 模型选择、运行目录、权限模式及已有 Skill 选择 |
| 设置 | 显示主目录、检测诊断和打开扩展管理的入口 | 不重复提供第二套编辑表单 |
| 反向代理 | 保持独立；MCP 若声明依赖某地址，仅显示明确的地址关系 | /v1 协议、路由、端口、认证、主备策略及 Key 权限 |
| 项目与任务 | 可从相关对话管理扩展，但关联不作为自动接入或修改授权 | 不因项目删除而删除全局扩展 |
| 日历与专注 | 页面跳转、审阅和检测期间继续正常运行 | 独立状态、计时、通知、任务撤销 |
| 外部 Daylight Skill | 同步扩展读取、prepare/actions、恢复的公开接口说明和命令 | 仓库 Skill 源码与独立安装仍分别更新，不自动发布安装 |

管理服务返回变更事件 {kind: extensions, revision, changedIds, operationId}。app.js 定向刷新扩展控制器；AI 操作链接跳到对象详情；其他页面不全量重绘。页面外部手动修改通过受限监听和进入页面时重扫发现，不静默回写源文件。

不在后台自动重启外部 CLI，不中止现有生成。已经加载到旧会话中的 Skill 内容不会因归档而自动从模型上下文撤回，界面要展示相应的后续生效说明。

**10. 人的操作习惯与可访问性**

按「找到来源 → 理解用途 → 看软件接入 → 预览影响 → 执行 → 核对结果」设计主流程，而不是让用户先理解内部架构。

初始清单给出用途和接入摘要，详细路径、参数、JSON/TOML 放到详情。普通新增、编辑由用户明确保存即可，不反复弹批准框；跨软件接入、归档、接管等有实际影响的操作展示一次具体预览。AI 发起变更沿用现有审阅卡。

编辑中的内容独立于服务快照。刷新、切分类、切软件、AI 应用和后台扫描不能清空 dirty 输入。离开页面时保留草稿；需要覆盖输入才提示处理。操作结束后焦点返回触发按钮，错误定位到字段或对应行，提示包含可以执行的下一步。

按钮可用键盘操作，分类控件复用方向键/Home/End，弹窗支持 Escape、焦点约束及恢复。重要动作不藏在仅 hover 出现的控件中；状态使用文字和图标，不能只靠颜色。

建议验证 1360×900、1024×768、800×600，200% 缩放，长路径、中文/英文长名称、多软件标签以及 loading/error/空状态。详情层不覆盖核心操作，固定栏不能遮住列表最后一行。沿用现有 spacing、标题与按钮 token；新增动效仅承担反馈并支持 prefers-reduced-motion。

**11. 性能与资源生命周期**

扫描只限定主目录和适配器登记的接入位置；不递归用户主目录、应用私有数据、历史会话或项目仓库。索引先读元数据，正文和资源按需读取；同 realpath 去重，错误以单对象诊断呈现。

页面可见时订阅状态变化；不可见时停止页面刷新，保留 dirty 表单；dispose 取消请求并清理监听。MCP 检测显式启动，最多同时两项，单项超时可取消，完成/失败/取消均清理自己创建的子进程和连接，不终止其他软件持有的 MCP 进程。

建议性能验收预算，均待实测确认：

- 缓存状态的页面交互 P95 小于 100 ms；
- 1,000 个合成 Skill 和 100 个 MCP 配置的缓存清单接口 P95 小于 300 ms；
- 同规模冷扫描目标小于 3 s，原生 helper 冷启动时间另外报告；
- 普通编辑不等待所有客户端运行验证；
- 无扩展操作时，任务与专注路径无新增扫描或 CLI 启动；
- 扩展扫描/检测压力下，任务查询 P95 相对同环境基线增幅不超过 10%，专注无额外漏记。

这些是拟议目标，不是已测结果；若实测不能满足，应定位扫描、主线程、队列或 helper 启动成本，再调整实现与预算。

**13. 最终验收条件**

| 用户场景 | 通过标准 |
| --- | --- |
| 打开扩展管理 | 清单只来自 ~/.agents；打开、筛选、查看不改源文件或启动 MCP |
| 编辑一个 Skill | 只有主文件改变；需要链接的软件仍指向该来源；原生读取软件不新增链接；读回内容一致 |
| 接入 Qoder | 预览具体目标；正确链接建立并被目标软件发现；冲突实体目录完全保留 |
| 查看 Codex/Pi 原生支持 | 说明无需链接；不自动删旧链接；运行发现另有验证证据 |
| 管理 MCP | 一处主配置生成对应适配文件；明确客户端是否接入；保存不自动执行 |
| 遇到不能链接的混合配置 | 显示真实限制与接入方式；不覆盖全局配置，不报告自动生效 |
| AI 查询或讨论 | 零写入；不自动创建任务、不触发软件安装或 MCP 进程 |
| AI 请求修改扩展 | 出现含真实差异的审阅卡；拒绝不修改；批准经同一 API 应用并同步页面 |
| AI 或页面提交后响应丢失 | 用原 requestId 查回执；重启后仍能核对；不重复创建链接或覆盖 |
| 主文件/目标文件被手动修改 | 旧预览被拒绝，保留输入，显示需要重算的差异 |
| 归档来源或解除接入 | 语义不同；展示影响；不删除未知链接和用户实体目录；可按当前版本恢复 |
| 页面切换或软件离线 | 未保存输入仍在；计时和其他页面正常；离线不导致全局报错 |
| 无 Node / 模型登录异常 | 扩展模块显示自身限制；任务、日历、专注仍工作；已安装模型与凭据不改 |
| 狭窄窗口、键盘和缩放 | 完成查找、编辑、接入预览、取消/确认与 AI 返回；无遮挡、焦点丢失或只能鼠标完成的步骤 |

验收报告分开标记代码规则、自动化合同、浏览器操作、实际软件发现、实际 App 和真实 MCP 业务权限。真实账号/授权不在可测试条件内时明确未验收，不把握手或模拟服务测试扩大为全部业务通过。

首次用户操作验收建议选 5 个任务：查找一个 Skill、判断它是否需要链接、接入一个需要链接的软件、让 AI 提出并应用一次修改、处理一次冲突。建议目标：无技术解释即可完成至少 4 项，且不能出现误删/覆盖；理解困难用观察到的行为修正文案和流程。该目标不是已进行的人因测试结果。

**14. 实施顺序与变更清单**

| 阶段 | 交付 | 出口条件 |
| --- | --- | --- |
| A. 确认契约 | 主文件布局、软件能力表、MCP 兼容边界、对象/接入模型 | 不再存在“链接成功等于加载成功”的歧义 |

| D. AI 变更联动 | 审阅共用、管理工具、提交恢复、操作跳转和定向刷新 | 页面与 AI 应用同一动作产生相同结果 |
| E. 软件与产品验收 | 本机软件验证、浏览器/原生交互、压力及旧功能回归 | 分层证据齐全，已知兼容限制明确 |

C 与 D 应作为同一次功能交付闭环，不能把“页面有管理，AI 以后再接”当作本需求完成。阶段划分用于降低修改风险，不削减首版已经要求的 AI 管理能力。
